# Eliminate Unwanted Conversational Commentary from AI Polish

Strictly enforce direct text-only output for AI text polishing, stripping all introductory filler phrases (such as "Here is how we change the tone:"), conversational preambles, and meta-commentary generated by the local Gemma 3 AI model.

## User Review & Critical Decisions

> [!IMPORTANT]
> The AI text rewriting feature is intended to act as an immediate drop-in replacement for the user's text in the keyboard and sandbox. Conversational chat artifacts and preambles degrade the typing experience and disrupt direct text insertion.

- **Confirmed Decision**: Strip all conversational intros, preambles, and commentary automatically both at the prompt level (negative constraints) and in the post-processing sanitization pipeline.
- **Graceful Fallback**: If an output contains only commentary without any usable refined text, or if the sanitization strips everything, preserve the user's original text rather than returning conversational chatter or crashing.

---

## 1. Overview & Core Concept

When a user triggers AI Polish (in proofread, professional tone, casual tone, or any rewrite mode), the model should return *only* the refined text. Small language models like Gemma 3 1B occasionally output conversational preambles such as:
- *"Here is how we change the tone:"*
- *"Here is the revised text:"*
- *"Sure, here is the text in a professional tone:"*
- *"Below is the updated message:"*

This implementation implements a robust **two-tier defense**:
1. **Prompt-Level Directives**: Explicit zero-preamble negative constraints in `GgufPolishEngine.kt`.
2. **Post-Processing Sanitizer**: Robust regex-based pattern matching in `AiOutputValidator.kt` that removes multi-line and single-line commentary prefixes, colons, and explanatory trailers before text is handed to the keyboard or editor.

## 3. Implementation Steps

### Step 1: Enhance `AiOutputValidator.kt`
- Expand `COMMENTARY_PREFIXES` and add regex patterns targeting conversational preamble variations:
  - `^here (is|are) (how (we|to) change the tone|the (revised|polished|edited|updated) text).*?:\s*`
  - `^here('s| is) (a |the )?(revised|polished|formal|professional|casual|rewritten) (version|text|tone).*?:\s*`
  - `^(sure|certainly),?\s*(here (is|are)|i have).*?:\s*`
  - `^(in a|with a) (professional|casual|friendly|business) tone:?\s*`
- Handle both multi-line commentary (where the preamble is on line 1) and inline commentary (where the preamble and text are on the same line separated by a colon or newline).
- Strip trailing explanatory notes like `\n\n(Note: ...)` or `\n\nExplanation: ...` if the model adds follow-up commentary at the end.
- Update `isValid()` so that if `sanitize()` successfully removed the preamble, the remaining text is validated cleanly without false rejections.

### Step 2: Reinforce `GgufPolishEngine.kt` Prompt Construction
- Update the system and user turn formatting in `GgufPolishEngine.prompt()`:
  - Add explicit negative constraints: *"CRITICAL: Output ONLY the raw final rewritten text. Do NOT include ANY introductory words, conversational filler, commentary, meta-talk, explanations, or quotes (such as 'Here is...', 'Here is how we change the tone:', or 'Sure'). Begin your response immediately with the very first word of the rewritten text."*
  - Reiterate that the response will be directly pasted into the user's document.

### Step 3: Add Robust Unit Tests
- Create tests in `AiOutputValidatorTest.kt` verifying:
  - Removal of `"Here is how we change the tone: <text>"`
  - Removal of `"Here is how we change the tone:\n\n<text>"`
  - Removal of `"Sure! Here's the revised version:\n<text>"`
  - Preservation of normal text starting with valid words (e.g. `"Here are five reasons why..."` if that was the user's actual text).

### Step 4: Verification & Build
- Run `compile_applet` and verify unit tests to ensure zero regressions in text polishing and input handling.
